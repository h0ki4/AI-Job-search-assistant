# AI Job Search Assistant

## About

AI Job Search Assistant is an async-first Python backend learning project. Its
goal is to help store vacancies, compare job requirements with user skills,
track applications and follow-ups, and later provide analytics and LLM-assisted
vacancy analysis.

The repository currently contains the Stage 0 foundation and an agreed design
for the first domain entity, `Vacancy`. No database tables or CRUD operations
have been implemented yet.

## Current Features

- one application entry point and one `asyncio` event loop;
- asynchronous SQLite connection through `aiosqlite`;
- a startup health check that executes `SELECT sqlite_version()`;
- a database path configurable with the `DATABASE_PATH` environment variable;
- automatic connection cleanup through an async context manager;
- a prepared minimal Docker image;
- an agreed `Vacancy` data contract, including source links and location data.

See [PROJECT_STATUS.md](PROJECT_STATUS.md) for the current stage, verified
checks, decisions, and the next implementation task.

## Architecture

```text
asyncio.run(main)
        ↓ await
open_database
        ↓
aiosqlite
        ↓
SQLite file
```

This is intentionally smaller than the future architecture. Services,
repositories, and domain modules will be added only when the corresponding
features exist.

## Tech Stack

- Python 3.14.7;
- `asyncio` from the Python standard library;
- SQLite 3.53.4 in the current local runtime;
- `aiosqlite 0.22.1`;
- Docker;
- Git.

The Docker image is pinned to Python 3.14.7.

Only `aiosqlite` is installed as a third-party Python dependency at this
stage. SQLite is supplied by Python/Homebrew and `asyncio` is part of Python's
standard library. FastAPI, SQLAlchemy, pytest, httpx, and other planned tools
will be versioned and installed only when their first concrete use case exists.

## Installation

Verify Python 3.14.7, then create and activate a virtual environment:

```bash
python3 --version
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

The application reads configuration from process environment variables. For a
local shell, copy the example and export its values:

```bash
cp .env.example .env
set -a
source .env
set +a
```

The application does not parse `.env` itself yet, so an extra dotenv dependency
is not required. PyCharm can set the same variable in the run configuration.

## Run

From the project root:

```bash
python -m app.main
```

The first run creates `data/job_search.db`. The database file is runtime data
and is ignored by Git.

## Docker

Build the image:

```bash
docker build -t ai-job-search-assistant .
```

Run it with persistent local database storage:

```bash
docker run --rm \
  --env-file .env \
  --mount type=bind,source="$(pwd)/data",target=/app/data \
  ai-job-search-assistant
```

The image is the packaged application environment. The bind mount keeps the
SQLite file on the host after a container exits. `asyncio` remains the Python
concurrency model inside that container.

Docker Compose is not included yet because the project currently has only one
container and no multi-service configuration to coordinate.

Docker Desktop is not installed on the current development machine, so the
Docker build and run commands have not yet been verified.

## Agreed Vacancy Design

The first table will represent one vacancy. It will store facts from an
external source; it will not store a user's application status or skills.

| Field | SQLite type | Required | Purpose |
|---|---|---:|---|
| `id` | `INTEGER` | generated by database | Unique vacancy identifier. |
| `position` | `TEXT` | yes | Job title. |
| `company` | `TEXT` | yes | Employer or available client name. |
| `url` | `TEXT` | yes | Direct link to the original vacancy. It will later be protected from duplicates. |
| `source` | `TEXT` | yes | Source such as `linkedin`, `upwork`, `headhunter`, or `manual`. |
| `location_raw` | `TEXT` | no | Location exactly as it appears in the source. |
| `country_code` | `TEXT` | no | Normalized target-market country code, for example `PL` or `DE`. |
| `city` | `TEXT` | no | City when the source provides one. |
| `work_format` | `TEXT` | no | `remote`, `hybrid`, or `office`; strict validation will come later. |
| `description` | `TEXT` | no | Original vacancy text for future skill and LLM analysis. |
| `notes` | `TEXT` | no | Personal notes about the vacancy. |
| `publication_date` | `TEXT` | no | Publication date when the source provides it. |
| `created_at` | `TEXT` | generated by application | When the vacancy was saved, in ISO 8601 UTC format. |

Location is deliberately split into raw and normalized data. `location_raw`
preserves the source text, while `country_code` enables reliable country-market
filtering without comparing inconsistent strings such as `Poland`, `PL`, and
`Warsaw, Polska`.

Future search criteria will belong to a separate `SearchProfile`, not to a
vacancy. It will eventually contain target positions, countries, cities,
allowed sources, and preferred work formats. This will let an importer or LLM
work within explicit user-defined markets.

## Tests

No test framework has been added at Stage 0. For now, running the application
checks both the event loop and the SQLite connection. Automated tests will be
introduced with the first business logic and database behavior.

## Roadmap

1. Create the first SQLite `vacancies` table and study primary keys, `NOT NULL`,
   and SQL constraints.
2. Add a small async vacancy repository one operation at a time.
3. Add services and a minimal CLI as real use cases appear.
4. Implement the pure-Python matching engine and its tests.
5. Add skills, applications, statuses, and follow-ups incrementally.
6. Add FastAPI only after the core application works independently of HTTP.
7. Later evaluate PostgreSQL, external vacancy sources, LLM integration, and
   analytics when they solve concrete project needs.
